# Spec: ne8000-nas-registration

**Capability**: `ne8000-nas-registration`
**Type**: Additive (idempotent seed migration — no new Prisma model)
**Change**: `network-audit-pages`
**Affected files**:
- `prisma/migrations/<timestamp>_ne8000_nas_registration/migration.sql`
- `src/domain/entities/nas.ts` — `NasType` extension
- Possibly `prisma/schema.prisma` — `NasType` enum or string field update

> The `NasServer` model already exists. This capability only REGISTERS the Huawei NE8000 BRAS
> as a row in that table so it can be used as a foreign key target for `RadiusEvent.nasId`
> and as the scope anchor for `ListNe8000PppoeAudit`.

---

## 1. Phase 0 Prerequisite — ✅ RESOLVED (2026-06-22)

### REQ-PRE-1: NE8000 `nasipaddress` CONFIRMED

**Given** the NE8000 BRAS appears in `radacct` with a specific `nasipaddress` value
**When** Phase 0 was executed (2026-06-22)
**Then** the confirmed value is **`nasIpAddress = '10.75.0.30'`** (sub-interface VLAN 75 `100GE0/5/0.75`; all ~162 active PPPoE sessions report under this single IP; single-box NE8000 M8, not dual)
**And** management `ipAddress` is also `'10.75.0.30'` (known L3 address of the BRAS toward RADIUS HA; no separate mgmt IP documented)
**And** the implementation MUST use the literal `'10.75.0.30'` for both `ipAddress` and `nasIpAddress`
**And** source of truth: `infra-ne8000/ESTADO-RADIUS-HA-NE8000.md` + `BRIEF-ACCESO-SUR-NE8000-20260621.md`

## 2. NasType Extension

### REQ-NASTYPE-1: `NasType` domain type gains `'huawei_radius'` variant

**Given** the existing `NasType` in `src/domain/entities/nas.ts`:
```ts
export type NasType = 'mikrotik_api' | 'mikrotik_radius' | 'cisco' | 'ubiquiti' | 'cambium' | 'other';
```
**When** this capability is implemented
**Then** `NasType` MUST be extended to include `'huawei_radius'`:
```ts
export type NasType = 'mikrotik_api' | 'mikrotik_radius' | 'cisco' | 'ubiquiti' | 'cambium' | 'huawei_radius' | 'other';
```

**And** the rationale for a new variant (not reusing `'mikrotik_radius'`) is: the NE8000 uses Huawei VSAs (`HW-Data-Filter` for rate limiting) which differ from MikroTik VSAs; enforcement code uses `NasType` to decide which VSA set to apply

### REQ-NASTYPE-2: `NasServer.type` in the DB stores the string `'huawei_radius'`

**Given** `NasServer.type` is a `String` field in Prisma (not an enum)
**When** the NE8000 row is inserted
**Then** the `type` column MUST be set to `'huawei_radius'`
**And** no migration to the `NasServer` table structure is needed (already `String`)

## 3. Idempotent Seed Migration

### REQ-SEED-1: NE8000 registered via `INSERT ... ON CONFLICT DO NOTHING`

**Given** the idempotent seed pattern used in this project
**When** the migration runs
**Then** the SQL MUST be:

```sql
INSERT INTO "NasServer" (
  "id", "name", "type", "ipAddress", "nasIpAddress",
  "status", "clientCount", "description", "createdAt"
) VALUES (
  gen_random_uuid(),
  'NE8000-1',
  'huawei_radius',
  '10.75.0.30',
  '10.75.0.30',
  'active',
  0,
  'Huawei NE8000-1 BRAS — PPPoE Acceso Sur (terminación RADIUS HA)',
  now()
) ON CONFLICT DO NOTHING;
```

**And** `ON CONFLICT DO NOTHING` ensures re-running the migration is safe
**And** if the row already exists (e.g. manually inserted), the migration MUST succeed without error

> Note: `<NE8000_MANAGEMENT_IP>` is the management/control-plane IP of the BRAS;
> `<NE8000_NAS_IP>` is the `nasipaddress` value as it appears in `radacct`. These MAY differ.
> Both MUST be confirmed in Phase 0.

### REQ-SEED-2: Migration MUST NOT hardcode a fixed UUID

**Given** `gen_random_uuid()` is available in PostgreSQL 13+
**When** the seed migration inserts the NE8000 row
**Then** the UUID MUST be generated by the DB at migration time (not hardcoded in SQL)
**And** the row's `id` MAY be referenced later by a constant in the application config
**And** a lookup by `nasIpAddress = '10.75.0.30'` is the preferred way to find the NE8000 at runtime

### REQ-SEED-3: Migration is generated via `prisma migrate dev`

**Given** the project convention (no hand-edited SQL in migration files)
**When** the seed migration is added
**Then** the migration folder MUST be created via `npm run prisma:migrate`
**And** the custom `INSERT ... ON CONFLICT` SQL MUST be added to the generated `.sql` file manually after generation (since Prisma does not generate seed data — this is the standard project pattern for seed migrations)

## 4. Runtime Lookup

### REQ-LOOKUP-1: NE8000 `NasServer` is resolved by `nasIpAddress` at runtime

**Given** the ingest scheduler processes a `RadiusEvent` with `nasIp = '10.75.0.30'`
**When** the scheduler resolves `nasId`
**Then** it MUST look up `NasServer` where `nasIpAddress = '10.75.0.30'`
**And** the found `NasServer.id` MUST be stored as `RadiusEvent.nasId`
**And** if the lookup fails (row not found), `nasId` MUST be `null` (never a hard failure)

### REQ-LOOKUP-2: `ListNe8000PppoeAudit` scopes query by NE8000 `nasId`

**Given** the `NasServer` row for the NE8000 has been inserted
**When** `ListNe8000PppoeAudit` executes
**Then** it MUST query `PppoeService` where `nasId = <NE8000 NasServer.id>`
**And** MUST NOT hardcode the NE8000's UUID — it MUST look it up by `nasIpAddress` or a named constant at startup

---

## 5. No Existing Data Impact

### REQ-COMPAT-1: Existing `PppoeService` rows are not modified

**Given** existing `PppoeService` rows that point to MikroTik `NasServer` IDs
**When** the NE8000 seed migration runs
**Then** no existing `PppoeService` row MUST be altered
**And** no existing `NasServer` row MUST be altered

### REQ-COMPAT-2: `NasType` extension is backward-compatible

**Given** existing `NasServer` rows with `type IN ('mikrotik_api', 'mikrotik_radius', 'other')`
**When** `NasType` is extended with `'huawei_radius'`
**Then** all existing rows remain valid (the field is `String` in Prisma — no enum migration needed)
**And** TypeScript code that switches on `NasType` MUST handle the new `'huawei_radius'` case explicitly (default `'other'` branch covers it for now)
